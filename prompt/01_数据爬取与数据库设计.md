# 01_数据爬取与数据库设计.md

本文件是 Trae 生成代码时的完整约束文档，涵盖从 12306 获取原始数据到构建基础数据库的全部实现细节。

**Trae 使用说明**：按以下顺序实现功能，所有接口地址、参数名、字段名、异常条件均已明确，无需猜测。


## 第一部分：数据爬取

### 1.1 车站列表采集

**目标**：获取全国所有车站的电报码（station_id）和中文名（station_name）

**接口完整信息**：

| 项目 | 值 |
|------|-----|
| 完整 URL | `https://kyfw.12306.cn/otn/resources/js/framework/station_name.js` |
| 请求方式 | GET |
| 响应编码 | UTF-8 |
| 关键请求头 | `User-Agent`（任意主流浏览器 UA），`Referer: https://kyfw.12306.cn/otn/leftTicket/init` |

**前置请求**：在请求 station_name.js 之前，先访问以下 URL 获取 Cookie：

```
GET https://kyfw.12306.cn/otn/leftTicket/init
```

**返回数据格式**：

```javascript
var station_names = '@bjb|北京北|VAP|beijingbei|bjb|0@bjj|北京西|BXP|beijingxi|bjj|1@...'
```

**解析规则**：
- 整体是一个字符串，以 `@` 分割每个车站
- 每个车站的字段以 `|` 分割：
  - 索引 0：简拼（如 `bjb`）
  - 索引 1：车站中文名（如 `北京北`）
  - 索引 2：电报码（如 `VAP`），即 `station_id`
  - 索引 3：全拼（如 `beijingbei`）
  - 索引 4：缩写
  - 索引 5：序号
- 需要字段：索引 1（station_name）和索引 2（station_id）

**代码实现要点**：
- 使用正则表达式提取 `var station_names = '([^']+)'` 中的内容
- 过滤掉首尾空条目（空字符串或 `@` 开头）
- 所有车站存入 `stations` 表，`station_id` 为主键


### 1.2 车站大屏接口（获取所有车次）

**目标**：遍历所有车站，获取每个车站当天的经停车次列表，从中提取所有 G 字头车次

**接口完整信息**：

| 项目 | 值 |
|------|-----|
| 完整 URL | `https://kyfw.12306.cn/otn/czxx/query` |
| 请求方式 | GET |
| 关键请求头 | 同 1.1，额外需要 `X-Requested-With: XMLHttpRequest` |
| Session | 复用 1.1 中获取的 Cookie |

**请求参数**：

| 参数名 | 类型 | 必填 | 说明 | 示例 |
|--------|------|------|------|------|
| `station_name` | string | 是 | 车站电报码 | `VNP` |
| `train_date` | string | 是 | 查询日期，格式 YYYY-MM-DD | `2026-07-02` |
| `pageIndex` | int | 否 | 页码，从 1 开始 | `1` |
| `pageSize` | int | 否 | 每页条数 | `50` |

**返回数据结构**（JSON）：

```json
{
  "status": true,
  "data": {
    "total": 150,
    "data": [
      {
        "station_name": "北京南",
        "station_telecode": "VNP",
        "train_no": "240000G110",      // 注意：这是内部编号，不是显示车次
        "station_train_code": "G1",    // 显示车次号
        "arrive_time": "----",         // 到达时间，"----" 表示无
        "depart_time": "07:00",        // 发车时间
        "stopover_time": "--",         // 停站时间
        "train_type_name": "高速动车"
      }
    ]
  }
}
```

**关键字段说明**：
- `data.data` 是数组，每个元素是一趟车
- `station_train_code`：显示车次号，如 `G1`
- `train_no`：12306 内部编号，用于后续调用车次详情接口
- `arrive_time` 和 `depart_time`：至少有一个不是 `"----"`

**分页逻辑**：
1. 首次请求不带 `pageIndex`（或 `pageIndex=1`）
2. 检查 `data.total` 字段获取总条数
3. 计算总页数：`totalPages = ceil(total / pageSize)`
4. 循环请求 `pageIndex = 2, 3, ...` 直到当前页 ≥ 总页数
5. 如果某次请求返回的 `data.data` 为空数组，停止翻页

**去重逻辑**：
- 所有车站的所有页面数据合并后，按 `station_train_code` 去重
- 只保留以 `"G"` 开头的车次（即 G 字头）
- 去重后得到 `{ station_train_code: train_no }` 映射表

**异常处理**：
- 如果某车站请求返回 `status: false`，记录日志后跳过该车站（不中断整体流程）
- 如果 `data.data` 不存在或不是数组，记录日志后跳过


### 1.3 车次详情接口（获取经停站）

**目标**：对每个已发现的 G 车次，获取其完整的经停站列表

**接口完整信息**：

| 项目 | 值 |
|------|-----|
| 完整 URL | `https://kyfw.12306.cn/otn/czxx/queryByTrainNo` |
| 请求方式 | GET |
| 关键请求头 | 同 1.2 |
| Session | 复用 1.1 中获取的 Cookie |

**请求参数**：

| 参数名 | 类型 | 必填 | 说明 | 示例 |
|--------|------|------|------|------|
| `train_no` | string | 是 | 内部车次编号（从大屏接口获取） | `240000G110` |
| `from_station_telecode` | string | 是 | 始发站电报码 | `VNP` |
| `to_station_telecode` | string | 是 | 终到站电报码 | `AOH` |
| `depart_date` | string | 是 | 出发日期，格式 YYYY-MM-DD | `2026-07-02` |

注意：`from_station_telecode` 和 `to_station_telecode` 是大屏接口中返回的该车次始发站和终到站，**不是**用户查询的区间。

**返回数据结构**（JSON）：

```json
{
  "status": true,
  "data": {
    "data": [
      {
        "station_no": 1,
        "station_name": "北京南",
        "arrive_time": "",
        "depart_time": "07:00",
        "stop_duration": 0,
        "distance": 0
      },
      {
        "station_no": 2,
        "station_name": "济南西",
        "arrive_time": "08:30",
        "depart_time": "08:33",
        "stop_duration": 3,
        "distance": 406
      }
    ]
  }
}
```

**关键字段说明**：
- `data.data` 是数组，按 `station_no` 升序排列
- `station_no`：站序（整数，从 1 开始）
- `station_name`：车站中文名
- `arrive_time`：到达时间，格式 `HH:MM`，空字符串表示无（始发站）
- `depart_time`：发车时间，格式 `HH:MM`，空字符串表示无（终点站）
- `stop_duration`：停站分钟数（整数）
- `distance`：里程（公里）

**`stop_time` 的取值规则（代码直接实现）**：
```
if arrive_time 不为空且 != "":
    stop_time = arrive_time
else:
    stop_time = depart_time
```
（即：有抵达取抵达，没有取出发）

**数据存储**：将返回的经停站列表存入 `train_stops` 表，同时将车次基本信息存入 `trains` 表（`train_num` + `train_no` 映射）。

**异常处理**：
- 如果 `status: false`，记录失败日志，等待后续统一补填
- 如果返回的 `data.data` 为空数组，记录异常，等待补填
- 如果经停站数少于 2（只有起点和终点或只有 1 个站），标记为异常


### 1.4 反爬策略（代码强制实现）

在每次发送 HTTP 请求前执行以下逻辑：

**限速**：
```python
last_request_time = 0.0  # 全局变量
min_interval = 0.15  # 可配置
elapsed = time.time() - last_request_time
if elapsed < min_interval:
    time.sleep(min_interval - elapsed)
last_request_time = time.time()
```

**分段休眠**：
- 每完成 50 次请求，额外休眠 5~10 秒（随机）
- 统计变量 `request_count += 1`，当 `request_count % 50 == 0` 时触发

**重试机制**：
- 最大重试次数：3
- 重试间隔：`min_interval * 5 * attempt`（attempt 从 1 开始）
- 仅在以下情况重试：HTTP 状态码非 200、响应内容非 JSON、JSON 中 `status != true`
- 3 次重试后仍失败，记录该车次/车站为“待补填”，继续执行下一个

**Session 管理**：
- 使用 `requests.Session()` 管理 Cookie
- 启动爬虫时先访问 `https://kyfw.12306.cn/otn/leftTicket/init` 获取会话
- 所有后续请求复用该 Session
- 如遇到 302 重定向，重新初始化 Session


### 1.5 基准日期配置

- 使用 `datetime.now() + timedelta(days=3)` 作为基准日期
- 格式化为 `YYYY-MM-DD` 字符串
- 所有接口的 `train_date` / `depart_date` 参数使用同一日期
- 如需更换日期，修改此配置项即可


### 1.6 终端补填（统一执行）

**触发时机**：所有车次的经停站信息爬取完成后，统一执行一次。

**扫描异常数据的判断条件**（代码遍历所有记录）：
- `stop_time` 为空字符串或 `None`
- `station_name` 为空字符串或 `None`
- `station_id` 为空字符串或 `None`（即站名无法映射到电报码）
- `stop_no` 不连续（如 [1, 2, 4, 5] 缺少 3）

**交互流程**（命令行实现）：

1. 逐条打印异常信息：
```
⚠ [1/5] 车次 G123 | 第3站 | 站名: 济南西 | 缺少 stop_time，请补填（格式 HH:MM，直接回车跳过）：
```
2. 用户输入时间（如 `08:30`）后更新该记录
3. 用户直接回车则标记为 `需要人工复核`，记录到 `manual_check.md`
4. 全部补填完成后，显示汇总：`共扫描 XXX 条记录，X 条异常，X 条已补填，X 条待复核`


### 1.7 爬取产出（写入数据库前的数据检查）

在写入 `data/railway.db` 之前，验证以下条件：
- `trains` 表至少有 1 条 G 车次记录
- `train_stops` 表至少有 1 条经停记录
- `stations` 表至少有 1 条车站记录
- 所有 `train_stops.station_id` 都能在 `stations.station_id` 中找到（外键完整性）


## 第二部分：数据库设计

### 2.1 数据库文件路径

| 文件 | 路径 | 说明 |
|------|------|------|
| 基础数据库 | `data/railway.db` | 只读，爬虫生成后不再修改 |
| 题目数据库 | `question/qXXX.db` | 由出题器生成，测试器读取 |
| 元数据文件 | `question/metadata.json` | 记录每个题目的状态 |

代码实现时，路径使用相对于项目根目录的路径，运行前确保 `data/` 和 `question/` 目录存在。

### 2.2 stations 表（车站概览）

**CREATE TABLE 语句**：

```sql
CREATE TABLE stations (
    station_id TEXT PRIMARY KEY,
    station_name TEXT NOT NULL
);
```

**索引**：无额外索引（主键已索引）

**数据来源**：从 station_name.js 解析获得

**生命周期**：爬虫启动时创建，爬虫完成后不再修改


### 2.3 trains 表（车次概览）

**CREATE TABLE 语句**：

```sql
CREATE TABLE trains (
    train_num TEXT PRIMARY KEY,
    train_no TEXT UNIQUE NOT NULL
);
```

**索引**：无额外索引

**数据来源**：从大屏接口去重获得

**生命周期**：爬虫启动时创建，爬虫完成后不再修改


### 2.4 train_stops 表（车次经停站详情）

**CREATE TABLE 语句**：

```sql
CREATE TABLE train_stops (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    train_num TEXT NOT NULL,
    stop_no INTEGER NOT NULL,
    station_id TEXT NOT NULL,
    station_name TEXT NOT NULL,
    stop_time TEXT NOT NULL,  -- 格式 HH:MM
    FOREIGN KEY (train_num) REFERENCES trains(train_num) ON UPDATE CASCADE,
    FOREIGN KEY (station_id) REFERENCES stations(station_id) ON UPDATE CASCADE,
    UNIQUE(train_num, stop_no)
);
```

**索引**：

```sql
CREATE INDEX idx_train_stops_train_num ON train_stops(train_num);
CREATE INDEX idx_train_stops_station_id ON train_stops(station_id);
```

**数据来源**：从 queryByTrainNo 接口解析获得

**数据完整性**：
- 同一个 `(train_num, stop_no)` 组合唯一
- `train_num` 必须存在于 `trains` 表中
- `station_id` 必须存在于 `stations` 表中


### 2.5 station_trains 表（车站经停车次）

**CREATE TABLE 语句**：

```sql
CREATE TABLE station_trains (
    station_id TEXT PRIMARY KEY,
    station_name TEXT NOT NULL,
    data TEXT NOT NULL,  -- JSON 数组
    FOREIGN KEY (station_id) REFERENCES stations(station_id) ON UPDATE CASCADE
);
```

**data 字段 JSON 格式**（代码生成）：

```json
[
  {"stop_num": "G1", "stop_time": "07:00"},
  {"stop_num": "G2", "stop_time": "07:15"},
  {"stop_num": "G3", "stop_time": "07:30"}
]
```

**生成逻辑**（代码实现）：
1. 从 `train_stops` 表中按 `station_id` 分组
2. 对每个 `station_id`，收集所有经过该站的车次
3. 每个车次取该站的 `stop_time`
4. 按 `stop_num`（车次号）排序（字典序/数字序）
5. 序列化为 JSON 数组写入 `data` 字段

**物化时机**：所有补填完成后，执行一次 `REFRESH MATERIALIZED VIEW station_trains`（实际上从 `train_stops` 聚合数据并 INSERT/REPLACE 到此表）。


### 2.6 跨库外键约束（代码层实现）

SQLite 不支持跨数据库外键，因此 `question/qXXX.db` 中的 `train_num`、`from_station_id`、`to_station_id` 无法通过数据库层面约束到 `data/railway.db`。

**代码层校验**（出题器生成或测试器读取时执行）：

```
function validate_ticket_record(train_num, from_station_id, to_station_id):
    // 1. 检查 train_num 是否存在于 data/railway.db 的 trains 表
    // 2. 检查 from_station_id 是否存在于 data/railway.db 的 stations 表
    // 3. 检查 to_station_id 是否存在于 data/railway.db 的 stations 表
    // 4. 全部通过 → 允许操作；任何一项不通过 → 拒绝操作并报错
```


### 2.7 执行流程（代码实现顺序）

```
1. 初始化数据库：创建 data/railway.db 及四张表
2. 获取车站列表：请求 station_name.js → 写入 stations 表
3. 初始化 Session：GET /leftTicket/init 获取 Cookie
4. 遍历所有车站：对每个 station_id 调用大屏接口（含分页）
5. 收集 G 车次：按 station_train_code 去重 → 写入 trains 表
6. 遍历所有车次：对每个 train_no 调用车次详情接口 → 写入 train_stops 表
7. 终端补填：扫描异常数据 → 用户交互补填 → 更新 train_stops 表
8. 物化 station_trains：从 train_stops 聚合生成 → 写入 station_trains 表
9. 数据验证：检查外键完整性、记录数合理性 → 输出报告
10. 基础数据库构建完成，关闭连接
```


## 第三部分：与其他模块的接口约定

### 3.1 向 02_API与工具定义.md 提供的数据访问能力

```python
# 以下为接口约定，不是代码实现
GET /api/train                 # 读取 trains 表所有 train_num
GET /api/station               # 读取 stations 表所有记录
GET /api/train/{train_num}     # 读取 train_stops 表中该车次的所有经停站
GET /api/station/{station_id}  # 读取 station_trains 表中该车站的所有经停车次
GET /api/routes                # JOIN train_stops 查同时经过两个车站的车次
GET /api/train/{train_num}/ticket  # 读取 question/qXXX.db 中的余票数据
```

### 3.2 向 04_出题器设计.md 提供的数据访问能力

- 读取 `stations` 表：校验车站是否存在
- 读取 `trains` 表：校验车次是否存在
- 读取 `train_stops` 表：获取车次的经停站列表（用于渲染半矩阵）

### 3.3 对 question/qXXX.db 的约束

- 所有 `train_num` 必须能在 `data/railway.db` 的 `trains` 表中找到
- 所有 `from_station_id` 和 `to_station_id` 必须能在 `data/railway.db` 的 `stations` 表中找到
- 出题器在写入前执行校验，不通过则拒绝保存
