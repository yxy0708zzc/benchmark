# 05_测试器与测评器设计.md（给 Trae 的完整提示词）

本文件是 Trae 生成代码时的完整约束文档，涵盖第五章（测试方法与打分）中测试器与测评器的全部内容：启动流程、交互逻辑、数据记录、评分机制、输出格式。

**Trae 使用说明**：按以下顺序实现。测试器和测评器共用同一后端服务，但功能独立。测试器负责调用被测模型并记录方案，测评器负责调用测评模型并辅助评分。两个 API key 在测试器启动时分别填写，互不影响，且不保存到任何配置文件中。

### 1.2 两个 API Key 的处理

| 项目 | 说明 |
|------|------|
| 被测模型 API Key | 调用被测大模型（如 DeepSeek-V3、GPT-4 等），测试其能力 |
| 测评模型 API Key | 调用测评大模型（可能不同厂商），用于需求拆解和实现判断 |
| 存储方式 | **不保存**，每次启动测试器时弹窗填写，仅当前会话有效 |
| 验证方式 | 填写后发送测试请求（如 `models` 列表或简单对话），验证通过后方可进入 |

**调用参数**：

```python
response = client.chat.completions.create(
    model="deepseek-v3",  # 用户指定
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},  # 来自 03_提示词设计.md

        # 以及历史对话（多轮）

```

**工具执行循环**：

大模型可能多次调用工具，测试器需要循环处理：

```
while True:
    response = client.chat.completions.create(...)
    if response.message.tool_calls:
        for tool_call in response.message.tool_calls:
            result = execute_tool(tool_call.name, tool_call.arguments)
            # 将 tool 结果追加到 messages
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": json.dumps(result)
            })
        # 继续循环，让模型处理 tool 结果
    else:
        # 模型给出最终答案
        break
```

**记录工具调用**：

每次工具调用及其返回值都要记录到日志中：

```python
tool_log = {
    "tool_name": "query_trains_between_stations",
    "arguments": {"from_station_id": "VNP", "to_station_id": "AOH"},
    "result": {...}
}
```

### 2.4 多轮对话支持

- 对话历史存储在 `messages` 数组中

### 3.3 阶段二：数据库核实（代码直接查，0 token）

**目的**：验证被测模型声称的票是否真实存在

**步骤**：

1. 从被测模型的最终方案中提取“声称的票”：
   - 车次号（如 `G1`）
   - 出发站（如 `VNP`）
   - 到达站（如 `AOH`）
   - 座位类型（如 `class2`）
   - 票数（如 `2`）

2. 连接当前题目的数据库：`question/{question_id}.db`

3. 执行查询：

```python
cursor.execute("""
    SELECT tickets FROM class2
    WHERE train_num = ? AND from_station_id = ? AND to_station_id = ?
""", ("G1", "VNP", "AOH"))
row = cursor.fetchone()
```

4. 判断：
   - 如果记录存在且 `tickets >= 声称票数` → ✅ 真实
   - 如果记录存在但 `tickets < 声称票数` → ❌ 造假（声称有票但实际不足）
   - 如果记录不存在 → ❌ 造假（声称有票但数据库无此记录）

**注意**：如果方案中涉及多个车次或多次购票（如换乘、同车换乘），对每个声称的票都进行核实。

## 第四部分：评分机制（核心公式）

### 4.1 单条需求评分（0/1/2）

| 分值 | 含义 | 示例 |
|------|------|------|
| 0 | 完全没有实现 | 用户要求2张票，方案买了1张 → 0分 |
| 1 | 基本实现但有偏差或部分满足 | 用户要求下午出发，方案是14:30出发，但只有1张票 → 1分 |
| 2 | 完全实现 | 用户所有要求全部精确满足 → 2分 |

### 4.2 总分计算

**步骤 1**：对每条需求生成 0/1/2 分

**步骤 2**：计算平均分

```
平均分 = sum(所有需求得分) / 需求总数
```

**步骤 3**：归一化到百分制

```
百分制得分 = (平均分 / 2) × 100
```

**示例**：

- 5 条需求，得分 `[2, 2, 1, 2, 2]`
- 总和 = 9，平均分 = 9/5 = 1.8
- 百分制 = (1.8/2) × 100 = **90 分**

### 4.3 “不存在结果”的处理

如果被测模型最终反馈“不存在结果”（即买不到票），测评流程为：

1. 测评器跳过需求拆解和数据库核实
2. 直接记录为“失败”
3. 人工复核确认模型是否合理（确实无票还是模型能力不足）
4. 保存结果：`{"status": "no_solution", "human_confirmed": true}`

**注意**：即使模型说“不存在结果”，仍需要人工确认其合理性。
